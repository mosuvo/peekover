## 0. Decisions SETTLED at this gate (2026-08-14)

**D-1 · THE APP-PAGE FIRST-PAINT HARNESS IS THE PLAN'S FIRST ARCHITECTURAL MOVE — a NEW, capability-free, query-gated production seam plus a Playwright driver mirroring `perf-first-paint.ts`'s shape. DECIDED — and flagged to gate 2 as the plan's most novel call.**
`decisions.md` entry: *"009 D-1 — the app-page first-paint harness drives the real built extension, and the seam it needs costs nothing unless a harness explicitly asks for it"*

§3.8's app-page-only ruling puts Shiki — an engine — on the app-page render path for the first time since M8 confirmed that path has **never had a first-paint instrument at all** (`progress.md`, D-11 (iii)'s carried trigger, confirmed again at M8 close: *"the next milestone that puts work on the app-page render path whose cheapness cannot be argued mechanically … funds the app-page first-paint harness before it ships that work"*). §8's M-2 cannot produce a real measurement without this, so it is scoped first, the way 008 task 5.1 built its own perf harness before measuring rather than measuring on faith.

**★ There is no scoped-but-unbuilt harness design to reuse — verified, not assumed.** `progress.md` names the carried hole three times (007 §4-5, 008 D-11 (iii), M8 close) and never once describes a design, only the trigger. **008 D-11 (iii)'s own words are the honest state**: *"the next planner who puts non-mechanically-cheap work on the app page inherits a CONDITION, not a memory."* 009 is that planner. This plan supplies the design 007/008 never had reason to.

**★ The blocker is real and already independently discovered, by a DIFFERENT M2 task, for a DIFFERENT reason.** `scripts/perf-folder-tree.ts`'s own header (task 6.2) states it in terms: *"per Task 0 the native picker cannot run headlessly, while the production app page exposes no injectable folder-source seam at runtime to stand a handle in… NOT automatable here without a stub masquerading as proof."* That task settled for qualitative human-gate confirmation instead. **009 cannot make that trade**, because §5's <165 ms gate is a **quantitative** requirement Shiki must not regress, and a human eyeballing a page cannot produce that number.

**The concrete blocker.** `entrypoints/app/main.ts:20-22`'s only programmatic file-selection seam, `__peekover.selectFile`, is `import.meta.env.DEV`-guarded and **stripped from the production build** — confirmed still true (verified this session). `perf-first-paint.ts` drives the **real, built, minified** `.output/chrome-mv3` package via Playwright's `--load-extension`; measuring anything less than that artifact (e.g. a `pnpm dev` build) is exactly the "stub masquerading as proof" 6.2's own header declines. So a harness that measures the real thing needs a real-thing-shaped way to hand the app page a document, and today there is none.

**The resolution: a NEW seam, inert unless explicitly invoked, that survives the production build.**

- `entrypoints/app/main.ts` gains a check for a URL search param — `new URL(location.href).searchParams.has('__peekoverHarness')` — present **only** on a URL a harness itself constructs. The real launch path (`background.ts`'s `action.onClicked` opening the bundled app page) never adds it, so on every real user visit this branch does not run.
- When present, it installs one global — `window.__peekoverHarness.openFromHandle(handle: FileSystemDirectoryHandle)` — that feeds `handle` through **exactly the production code path** `openFolder()` already runs after `showDirectoryPicker()` resolves (`chromiumFolderSource.ts:98`, `folderSourceFromHandle`), skipping only the picker call itself. This is not a new capability: `folderSourceFromHandle` is not test-only scaffolding — it is the real function `openFolder()` calls in production, already reused by `tests/browser/folderGrant.browser.test.ts` and `tests/browser/folderDrop.browser.test.ts` for exactly this reason (a real `FileSystemDirectoryHandle` an OPFS-backed harness can construct with **no user gesture**, `navigator.storage.getDirectory()` needing none).
- **Why this adds no capability, stated as a property rather than an assertion:** the seam accepts a handle the CALLER already had to construct (OPFS, in-origin) — it does not grant folder access, it only removes a UI dialog for a caller that could reach the same folder data through no other route than one it already possesses. It ships no new manifest key, no new permission, no `web_accessible_resources` entry — `chrome-extension://<id>/app.html` is not web-accessible to an outside page by construction, so only a script already running in the extension's own origin (i.e., a driver that has already loaded the extension page, exactly what Playwright's `--load-extension` does) can reach `window.__peekoverHarness` at all.
- **The harness script**, new (`scripts/perf-app-first-paint.ts` or similarly named — `tasks.md`'s call), mirrors `perf-first-paint.ts`'s shape verbatim: same `chromium.launchPersistentContext` + `--load-extension` pattern, same `ITERATIONS = 7` / median-and-floor statistics, same `GATE_MS = 165`. It navigates `app.html?__peekoverHarness=1`, populates an OPFS directory with the same golden huge-document fixture `perf-first-paint.ts` already uses (`tests/golden/hugeDoc.ts`, so the two numbers are comparable), calls `window.__peekoverHarness.openFromHandle(dir)`, and times to the paint the content-script harness already times to.

*Rejected:* driving a `pnpm dev` (unminified, unbundled) build instead of adding a seam — this is the "stub masquerading as proof" 6.2's own header names and rejects; a dev build's parse/execute cost is not the shipped cost, and the whole reason D-11 (iii) exists is to stop the app page from shipping non-mechanically-cheap work unmeasured. **Reusing `__peekover.selectFile` by simply un-guarding it from `DEV`** — rejected because it is typed to accept an already-read `MarkdownFile`, not a folder, and widening it to accept a folder handle is the same amount of new code as a dedicated seam without the query-param inertness property; a bare global with no gate at all would also be reachable by any script that ever runs in that page's origin, which the query-param check avoids by construction.

**★ Flagged to gate 2 as the plan's single most novel call**, because it is new code that ships to the production bundle for the first time to serve an automation need rather than a product need — see Gate-2 Q1. The measurement this harness produces (§8 M-2) is what makes the app-page-only surface decision (§3.8, sealed) honestly priced rather than merely argued; without it, 009 would ship Shiki on a path 008 already confirmed cannot be argued mechanically, with nothing in its place.

**D-2 · THE ENGINE MODULE IS `src/render/codeEngine.ts`, THE ONE PLACE NAMING `import('shiki/...')`, AND THE FENCE IS `src/render/codeImportFence.test.ts`, MIRRORING `diagramImportFence.test.ts`'S FOUR CLAUSES EXACTLY. DECIDED.**
`decisions.md` entry: *"009 D-2 — the lazy-chunk fence for Shiki is the same structural proof 007 built for Mermaid, over a different pair of modules"*

§3.2 names the precedent as exact and names `plan.md`'s job as picking the module name. `codeEngine.ts` (not `shikiEngine.ts`) matches `diagramEngine.ts`'s own convention — the module is named for the **capability** (diagrams / code), not the vendor (mermaid / shiki), which is the generic-noun discipline `diagramEngine.ts`'s header already establishes and this plan continues rather than reinvents.

- **Clause A** (`src/render/codeImportFence.test.ts`, walking `entrypoints/peekover.content.ts`): the content-script graph reaches neither `codeEnhancer.ts` nor `codeEngine.ts`, by any edge, and imports no `shiki` specifier anywhere. This is §3.8's app-page-only surface decision stated as the module graph — the same discipline `diagramImportFence.test.ts:31-34` states for clause A.
- **Clause B** (the app-page graph, walking `entrypoints/app/main.ts`): MUST reach both modules and MUST import `shiki` — the control that proves clause A is a real absence, not a broken walk (`diagramImportFence.test.ts:35-38`'s exact reasoning, re-applied).
- **Clause C, the laziness pin**: exactly one dynamic `import('shiki/...')` edge in the whole tree, in `codeEngine.ts`, and it must resolve DYNAMIC — a static `import shiki from '...'` anywhere would make the chunk eager on whatever graph `codeEngine.ts` sits in, which the byte fence alone cannot see (`diagramImportFence.test.ts:339-346`'s reasoning, unchanged).
- **Clause D, traversal non-vacuity**: both graphs are non-trivial with named landmarks, and every local specifier resolves — an unresolved edge is a hole the fence cannot see through (`diagramImportFence.test.ts:46-54`, re-applied verbatim).

**★ One structural difference from 007's fence, forced by D-3 below, not by taste.** D-13's mermaid fence has exactly one static `mermaid` specifier permitted (`mermaid/package.json`, a version-only JSON leaf). Shiki's own version is available the same way (`shiki/package.json`), **but D-3 below also names a second permitted static specifier** — `shiki/engine/javascript`, the regex-engine module, which per D-3's reasoning **carries no grammar/theme data and must itself stay off the eager graph's byte-weight** (bundled, not lazy — the JS-regex engine is orders of magnitude smaller than a language grammar set and its own header should say so when it lands). Clause C's assertion is written to expect **two** permitted non-dynamic `shiki`-family specifiers (the package-json leaf and the JS engine's own small module), not one, and the task that writes it must not silently copy 007's "expect exactly one" shape.

**D-3 · THE REGEX ENGINE IS `shiki/engine/javascript` — NO WASM, NO CSP CHANGE. RESOLVES §7-2 WITHOUT AN AGENTS.md #4 EVENT. DECIDED, verified against Shiki's current official docs, not memory.**
`decisions.md` entry: *"009 D-3 — Shiki ships two regex engines and 009 takes the one that keeps the manifest untouched, because the JS engine now covers every built-in grammar"*

Verified this session against `shiki.style`'s own current guide (not training-data memory, per AGENTS.md's standing rule, with the spec's own "more force than usual" applied because no dependency in this tree has raised the WASM/CSP question before):

- **Shiki's DEFAULT is the Oniguruma engine, and it DOES require WebAssembly.** `createHighlighter`/`codeToHtml`'s default configuration loads `shiki/wasm.mjs`, a WASM binary, alongside the theme and language data.
- **A pure-JavaScript alternative exists and is a first-class, documented path**: `import { createJavaScriptRegexEngine } from 'shiki/engine/javascript'`, passed as the `engine` option. As of Shiki 3.9.1 (009 is verifying against 4.4.3, newer) **every built-in language grammar is supported** — the accuracy gap the docs name (`forgiving: true` for unsupported grammars) does not apply to the bundled set.
- **The CSP fact, verified against Chrome's own current manifest docs, not memory**: MV3's DEFAULT `content_security_policy` for extension pages is `script-src 'self'; object-src 'self'` and **explicitly disables WebAssembly** under that default — instantiating WASM requires adding `'wasm-unsafe-eval'` to `script-src`, which requires a NEW `content_security_policy` manifest key Peekover's manifest does not carry today (confirmed: `tests/manifest.test.ts` pins `permissions: []` and no other trust-relevant key; no `content_security_policy` key exists in `wxt.config.ts`). **This is precisely spec §3.10's named AGENTS.md #4 trigger, and it fires if and only if the Oniguruma path is taken.**

**009 takes the JavaScript engine, and that choice is what discharges the risk rather than escalates it.** `codeEngine.ts` imports `createHighlighterCore` (or the equivalent fine-grained entry, D-4) with `engine: createJavaScriptRegexEngine()` — never the `shiki` package's top-level shorthand (`codeToHtml`), which pulls the Oniguruma/WASM path by default and would put the WASM binary on the app-page chunk regardless of whether it is ever instantiated (a bundler cannot prove a config object's `engine` field is never the default one without the import graph itself naming the alternate module). **The manifest, `permissions: []`, and `tests/manifest.test.ts` (2975 B) all stay untouched by this milestone** — §3.10's own EARS line (*"unless §3.10's WASM/CSP risk resolves to require one — in which case that is an AGENTS.md #4 event"*) does not fire, because the risk resolves to NOT requiring one.

★ **Revisit-when, named rather than silently possible:** if implementation measurement (M-1) or a later walk finds the JS engine's performance or a specific grammar's fidelity inadequate for a real document in this repository's own corpus, switching to the Oniguruma engine at that point **would be** the AGENTS.md #4 event this plan avoids today — routed to a human then, not decided now, and not a reason to default to the heavier path pre-emptively.

*Rejected:* the Oniguruma/WASM default (routes to a human before implementation, per spec §3.10 verbatim, and there is no forcing reason to spend that gate when the JS engine covers the whole bundled grammar set). Shipping both engines and choosing at runtime (doubles the byte cost D-2's fence and §8 M-1 must account for, for a fallback path nothing in this milestone's scope needs).

**D-4 · SHIKI'S OUTPUT NEVER BECOMES AN HTML STRING. THE ENHANCER BUILDS DOM DIRECTLY FROM `codeToTokens`'S STRUCTURED RESULT. NO NEW SANITIZER PROFILE. DECIDED — resolves §7-4.**
`decisions.md` entry: *"009 D-4 — code highlighting never produces markup to sanitize, because Shiki's token API hands back data, not a string"*

§7-4 poses the choice as 007's SVG-profile shape (a second sanitizer, D-1 there) or 008's table-tools shape (DOM built directly, "never as an HTML string," §5's own citation). The code answers it by what the engine actually offers, not by symmetry with either precedent:

- **`codeToHtml` produces an HTML string** (`<pre class="shiki" style="background-color:#…"><code>…<span style="color:#…">tok</span>…</code></pre>`) — inline `style` attributes throughout, which the document sanitizer profile explicitly forbids (`sanitize.ts:47-50`: *"Deliberately absent: style (no inline CSS)"*) and which 007's own SVG-profile precedent shows is real, reviewable work to admit safely (007 D-1's `<style>`-element CSS-cleaning pass exists for exactly this class of problem).
- **`codeToTokens(code, { lang, theme, structure: 'classic' })` returns structured line/token data — colors, font-style flags, text — with no HTML anywhere in the return value.** The enhancer walks that structure and calls `document.createTextNode` / `element.style.color = …` / `span.className = …` itself, the same shape `tableTools.ts` already uses for its own DOM construction (§5, AGENTS.md #3: *"every new node is built as DOM, never as an HTML string"*, 008 §1.3's own words for table sort/filter/copy). **No `innerHTML` assignment exists anywhere in the highlighting path**, which is a stronger guarantee than a reviewed allow-list: there is no string for a profile to have a gap in, because no string is ever produced.
- **What this buys, concretely:** `sanitize.ts`'s three existing consts (`ALLOWED_TAGS`, `ALLOWED_ATTR`, `SANITIZE_CONFIG`) and 007's SVG-profile arrays stay **byte-untouched** — `sanitize.ts` is not touched by 009 at all. No `USE_PROFILES`, no new allow-list to review, no `data:`-URI reasoning to redo (there is nothing in a token stream that can carry a URI at all).
- **Per-token colour values come from Shiki's OWN theme data**, not from markdown source — the same "generated artifact, not untrusted input" property 007 D-1 argues for the SVG profile applies here even more simply, because there is no markup surface for that artifact to abuse in the first place.

*Rejected:* `codeToHtml` + a third named sanitizer profile (007's shape, transplanted) — real, reviewable work (a `style`-attribute allow-list, a colour-value regex) to solve a problem D-4's alternative does not have. `USE_PROFILES` widening (not applicable — the document profile still must never learn `style`, and this path never touches it).

**D-5 · THE ENHANCER RUNS FROM THE SAME TWO APP-PAGE CALL SITES 007 D-12 ESTABLISHED — `readerPane.ts` AND `appShell.ts`'s render closure — AND NO OTHERS. `mount()` IS TOUCHED AT ZERO SITES. DECIDED.**
`decisions.md` entry: *"009 D-5 — code highlighting inherits 007's two-call-site shape unchanged, because 009 is a single-surface feature exactly like Mermaid, not a two-surface one like table tools"*

§3.3 requires the enhancement run after `mount()` returns and never become a branch inside it (006 D-15, unchanged); §3.8 (sealed) makes 009 an **app-page-only** feature, structurally identical to 007's Mermaid decision and NOT like 008's table tools, which needed all four of D-6's call sites because table tools shipped to both surfaces.

- Re-verified this session: `readerPane.ts:181` (`mount(outcome.text, host, { contained: true })`) is immediately followed at `:185-186`/`:198-200` by `enhanceDiagrams(host)` and `enhanceTables(host)` — the initial-select path. `appShell.ts:154-156` (`renderWithDiagrams`, the watch re-render closure) calls `mount`, `enhanceDiagrams`, `enhanceTables` in the same order. **`enhanceCode(host)` is appended after both**, at both sites — third in the list, after diagrams and tables, for no ordering reason beyond "newest last" (there is no code-inside-a-diagram or code-inside-a-table case in this pipeline that would force an order; markdown-it fences and GFM tables are siblings, and mermaid fences do not nest tables).
- **The content-script call sites (`mountReader.ts:90`, `contentWatch.ts:121`) are explicitly NOT touched** — the exact opposite of 008 D-6's site-4 finding, and for the opposite reason: 008 needed a fourth site because table tools shipped everywhere and a missed site was a shipped defect; 009 must NOT gain a fifth import there, because §3.8 (sealed) forbids the content-script reader from ever learning `codeEnhancer` exists. D-2's clause A is the test that would catch a mistake here.
- **`mount()` is touched at zero sites**, the same checkable property 007 states for itself (`plan.md` §2, 007): *"007 touches `mount.ts` at zero sites, and that is a checkable property, not an aspiration."* 009 inherits it unchanged; there is no code-block-specific chrome inside `mount()`'s `children[]` list (no badge, no toolbar-as-sibling — the toolbar lives INSIDE `.peekover-reader`, beside its block, built by the enhancer after the commit, not by `mount()`).
- **The cooldown constraint** (007 D-12's second reason: `watchController.ts:422` times the whole synchronous block for the cost-proportional cooldown) applies unchanged: `enhanceCode`'s entry point must be synchronous and return immediately, same shape as `enhanceDiagrams`'s documented prologue (`diagramEnhancer.ts:1-19`).

*Rejected:* a third call site pattern of any kind (nothing 009 does needs one) · reaching the content script "for consistency with table tools" (008 §3.7's own reasoning for going to both surfaces — storage/engine-byte reasons — is the reasoning 009's own spec §3.8 cites and explicitly declines to repeat: *"Shiki is the opposite case — it is an engine"*).

**D-6 · THE RETAINED SOURCE `<pre><code>` IS THE COPY SOURCE OF TRUTH, NEVER A SEPARATE DATA-ATTRIBUTE COPY — MIRRORING 007 D-15 EXACTLY. DECIDED — resolves the raw-copy half of §7-5.**
`decisions.md` entry: *"009 D-6 — the plain fence stays in the tree as the thing highlighting decorates, so the raw text it holds never needs a second copy"*

§3.6's first bullet is explicit that a naive `textContent`-walk of the HIGHLIGHTED markup risks whitespace fidelity loss "across some tokenizer versions" — a real, stated risk, not a hypothetical this plan invents. §4's copy criterion requires the exact-as-authored source. D-4 already means the highlighted result is built as sibling DOM (spans with inline colour, never a markup string) rather than an in-place `innerHTML` mutation of the original `<code>` — so the natural structure is 007 D-15's, reused rather than reinvented:

- **The original `<pre><code class="language-…">` markdown-it/sanitize already committed is RETAINED, not removed, not mutated.** A sibling structure — `codeToView.ts`'s `<div class="peekover-code">` wrapping BOTH the retained `<pre>` (hidden once highlighting succeeds) and the newly-built highlighted `<pre>` (or, on any of §3.9's three failures, the retained `<pre>` stays the ONLY visible thing, exactly D-15's "degradation is the default state, success is the mutation").
- **The toolbar's copy control reads `pre.textContent` off the RETAINED, untouched node** — never off the highlighted sibling, never a duplicated string in a data attribute or a closure. This costs zero extra bytes per block (the text already exists once, in the DOM, as it does today) and is exact by construction: nothing has touched it.
- **The fence seam is the same one 007 confirmed empirically**, not re-derived: `parse.ts` installs no custom fence renderer for the LANGUAGE CLASS shape (D-8 below adds one narrow additive case for META, not for this), markdown-it's default `<pre><code class="language-js">` survives sanitization untouched (`tests/golden/output/code.html:1-3`, re-verified this session — the committed golden literally shows this exact shape for a labelled and an unlabelled fence).

*Rejected:* capturing the raw text into a `data-*` attribute or a closure at enhancement time (§3.6's own text names this as ONE option — "in a data attribute, a closure, or equivalent" — but D-15's retained-node shape is strictly cheaper: zero duplication instead of one copy per block, and it is the pattern already reviewed and shipped for exactly this "keep the source, decorate around it" problem). Deriving copy text from the highlighted DOM's `textContent` (the specific risk §3.6 itself names and declines).

**D-7 · TOKENIZATION AND THE TOOLBAR ARE ONE ENHANCER, `codeEnhancer.ts`, NOT TWO — A DIFFERENT ANSWER FROM 008 D-6'S, FOR A STRUCTURAL REASON, NOT A PREFERENCE. TOOLBAR STATE IS PER-RENDER, MIRRORING 008 D-9. DECIDED — resolves §7-6.**
`decisions.md` entry: *"009 D-6 — highlighting and its toolbar are one enhancer because they are one feature over one fence set, unlike diagrams and tables which were two features over two independent DOM predicates"*

§7-6 asks this by direct analogy to 008 §7-9/D-6 (*"no shared post-mount enhancement seam… the fence being worth more than the DRY"*). **The analogy does not transfer, and the reason is structural, not a re-litigation:**

- **008 D-6 solved "should `enhanceDiagrams` and `enhanceTables` — two independently-scoped features, reachable from different surface sets — share ONE call-site composition point." The answer was no, because that composition point would have put `diagramEnhancer` on the content-script graph** (tables shipped everywhere, diagrams did not). **009 has no such asymmetry to protect**: highlighting and the toolbar are BOTH app-page-only (§3.8, sealed), both operate over the identical fence set (`pre > code[class^="language-"]`), and neither has an independent existence — a toolbar with no highlighted block beneath it is not a feature §3.1 scopes. There is no second surface for a shared seam to leak onto, so the fence-hazard argument that forced 008 D-6's split does not apply.
- **So `codeEnhancer.ts` does both in one synchronous-prologue-plus-async-body pass** (D-1's/007's shape): for each fence, build D-6's retained/highlighted pair AND the toolbar controls (copy, line-numbers toggle, line-highlight application, word-wrap toggle) in the SAME per-fence unit of work, because §3.6's toolbar controls act on the SAME element D-4 just finished tokenizing — walking the fence set twice (once to highlight, once to instrument) would read the DOM an extra time for no isolation benefit, since both walks are already confined to the identical selector on the identical surface.
- **Collapsible long blocks (§3.6, the ⭐ item) are the ONE part of this feature that is conditional on a DIFFERENT predicate — block length, not "is this a fence" — so it composes as a THIRD step in the same per-fence pass**, not a separate enhancer: after highlighting and wiring the toolbar, measure the retained/highlighted content's line count and apply D-10's collapse structure if over threshold. Still inside `codeEnhancer.ts`, because a block-length check has nowhere useful to run except after the block exists.
- **Toolbar state does not survive a watch re-render — mirroring 008 D-9 exactly, confirmed by the SAME structural argument, not newly argued.** `mount()`'s `replaceChildren` (`mount.ts:218`) discards the whole reading column on every re-render, `preserveReading` (`mount.ts:49-67`) carries only the scroll anchor and the view mode — never table state (D-9's own text) and, by the identical property, never code-toolbar state. A watch re-render that changes a fence's content leaves no stale line-numbers-on / word-wrap-on / expanded flag to be wrong, because there is no node left to carry one. §8-4's chosen DEFAULTS (line-numbers on/off, word-wrap on/off) apply fresh on every render, the same "unsorted is the resting state" shape D-9 states for tables.

*Rejected:* a shared cross-feature enhancer registry (008 D-6's own rejection, for the same reason: it would make the fence's static-graph guarantee a runtime one) — moot here since there is no second surface to guard against, but named so it is not "discovered" as an option later. Splitting tokenization and toolbar into two enhancers "for separation of concerns" — the DRY-vs-fence argument that would justify a split (008's) does not exist for a single-surface feature, and a split here buys an extra DOM walk for no isolation.

**D-8 · FENCE-META (`{2,4}`) DOES NOT SURVIVE MARKDOWN-IT'S DEFAULT FENCE RENDERER — VERIFIED EMPIRICALLY, NOT ASSUMED — AND REACHING IT POST-MOUNT REQUIRES A SMALL, ADDITIVE, CONDITIONAL `parse.ts` CHANGE. THIS CORRECTS THE SPEC'S §3.6/§7-3 FRAMING. DECIDED.**
`decisions.md` entry: *"009 D-8 — the fence's full info string never reaches the DOM by default, so line-highlighting needs one conditional attribute markdown-it does not emit today, not a DOM re-derivation that has nothing to read"*

**★ This is a genuine correction to the spec, not a restatement of it, and it is named here per the spec's own instruction (§ Evidence base) rather than silently patched.** §3.6 states: *"The meta string is already present on the markdown-it fence token's `.info` field at parse time; reading it is not a parser change… as long as the highlighting behavior stays a post-mount read of that already-parsed info string rather than a new parse-time feature."* §7-3 poses the open question as "does the enhancer receive the info string, or does it re-derive it from the DOM." **Verified this session, empirically, against the real parser** (`node -e` over the installed `markdown-it` 14.3.0, the exact production configuration `parse.ts:42` builds):

```
input:  ```js {2,4}\nconst x = 1;\nconst y = 2;\n```
output: <pre><code class="language-js">const x = 1;\nconst y = 2;\n</code></pre>
```

**The `{2,4}` is not in the output at all — not in a class, not in an attribute, nowhere.** markdown-it's default fence rule (`markdown-it/lib/renderer.js`'s `fence` renderer, not overridden anywhere in this tree — confirmed, `parse.ts` installs no custom rule) takes only the FIRST whitespace-delimited token of the info string (the language) and discards the rest. So **neither of §7-3's two named options is available**: the enhancer cannot "receive the info string" (nothing downstream of `parse()` has it) and cannot "re-derive it from the DOM" (there is nothing in the DOM to re-derive it from). The spec's own "not a parser change" framing is the part that does not hold; the underlying INTENT — read it post-mount, do not make highlighting a parse-time feature — is preserved by the resolution below.

**The resolution: `parse.ts` gains ONE additive, conditional custom fence renderer, and it changes output ONLY when a fence carries meta beyond its language.**

- A `md.renderer.rules.fence` override that calls markdown-it's own default fence rendering (via `Renderer.prototype.rules.fence` or the token's own `.info` field) and, **only when `info.trim().split(/\s+/).length > 1`** (i.e. there is a language AND something after it), appends one attribute — `data-fence-meta="{2,4}"` (the raw remainder of the info string, HTML-escaped) — to the emitted `<code>` element, alongside the `class="language-…"` it already gets.
- **Every existing fence with no meta is byte-identical output**, because the conditional never fires for them — this is what keeps `tests/golden/output/*` untouched (re-verified: none of the four committed golden fence fixtures — `code.html`'s labelled fence, unlabelled fence, indented block, inline code — carry meta beyond a language word, so the conditional's negative branch is exercised on 100% of today's corpus and changes nothing).
- **This is still "one parser, one instance"** (AGENTS.md's rule, `parse.ts:9-10`'s own stated discipline) — no second markdown-it instance, no new parsing pass, no new markdown syntax recognized; it is a renderer-level addition to how an ALREADY-parsed token is serialized, the same category of change GFM tables and task-list checkboxes already are in this file.
- **`codeEnhancer.ts` reads `code.dataset.fenceMeta`** post-mount and parses the `{2,4}` line-range syntax itself (a small pure function, unit-tested without touching `parse.ts` again) — this half of §7-3's intent (highlighting BEHAVIOR is a post-mount concern, not a parse-time one) holds exactly as the spec wanted; only the plumbing that gets the string there needed correcting.

**★ Flagged prominently: this DOES touch `parse.ts`, which the spec's Files-list framing (by omission — §7-3 never names `parse.ts` as touched) did not anticipate.** It is named here as a gate-2 finding per the instruction to flag rather than silently correct a sealed document's assumption. The change is additive, conditional, and does not widen the GFM rule set or `ENABLED_RULES` — a narrower footprint than it might sound, but a real one.

*Rejected:* re-deriving meta from the DOM (§7-3's second option — nothing is there to derive it from, verified). A second parser pass over the raw source to extract fence meta independently of markdown-it (violates the one-parser rule far more seriously than the additive renderer override does — it would mean two things disagreeing about where a fence starts and ends on malformed input). Encoding meta into the `class` attribute itself (e.g. `class="language-js" data-meta` vs. squeezing `{2,4}` into the class string) — a class is not the right carrier for a value with commas and braces, and `class` is also the selector `hasDiagramFence`/D-2's clause A pattern-matches on; adding noise to it risks a false match.
